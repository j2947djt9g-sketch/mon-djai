# Clair Fluidity 1, 2 and 4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Implement the three UX proposals approved by the user without changing financial calculations.

**Architecture:** Keep the existing single-page application and its embedded source mirrors. Store only a non-sensitive first-visit marker for the intro; reuse the current transaction submit boundary; explain incompatible filters with an explicit action.

**Tech Stack:** Plain JavaScript/HTML/CSS, Node VM regression suites, Playwright browser suites with fictional fixtures.

**Spec:** `docs/superpowers/specs/2026-11-05-fluidity-124-design.md`

## Global Constraints

- Preserve the full Clair name animation on first visit; never display account data before the existing account gate permits it.
- Preserve drafts when switching a new transaction between expense and income, and keep existing transaction corrections unchanged.
- Keep savings transfers separate from income/spending totals; filter recovery must preserve the other selections.
- Keep canonical `accounts/*.js` snippets and their embedded copies identical.
- Publish only the approved changes after independent review and passing checks; user selected 1, 2, 4 and instructed continuation. No real accounts, live backend writes or new dependencies.

## Review Focus

- Unavailable browser storage must not stop opening the application.
- A returning visitor with a slow or failed session must not see stale account data.
- Switching transaction type must preserve typed values and valid categories, including personal categories.
- An existing or automatic operation must not gain a type toggle that changes its financial meaning.
- Savings category and savings origin must both lead to the explicit filter recovery action, preserving the search and month.
