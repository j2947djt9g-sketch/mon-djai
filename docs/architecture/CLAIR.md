# Architecture Clair

Clair conserve le JSON v3, les centimes entiers, les huit devises et les dates civiles Paris. Son HTML autonome est assemblé depuis des sources versionnées ; aucune dépendance réseau supplémentaire n’a été introduite par l’extraction.

## Sources et frontières

- `clair/domain/engine.js` possède tous les calculs et expose l’API historique `ClairEngine`. `normalize` valide et retourne un nouveau budget ; `sync` modifie seulement le brouillon fourni. Le moteur ne connaît ni stockage, DOM, authentification, ni réseau. La normalisation accepte aussi les sauvegardes historiques compatibles ; elle ne doit pas remplacer systématiquement les candidats à enregistrer, car certains champs/defaults compatibles seraient projetés.
- `clair/application/budget-commands.js` prépare un candidat isolé : callback synchrone, validation complète, rattrapage automatique, nouvelle validation et contrôle épargne, puis copie détachée. `validateBudgetCandidate` est aussi appelée à l’entrée commune `saveData` des imports/réinitialisations. Les constructeurs de saisie manuelle, Express et épargne restent distincts. Une Promise/thenable retournée par un changement est refusée avant persistance.
- `clair/application/budget-session.js` est l’unique propriétaire du budget UI. `create({owner,epoch,budget})`, `getSnapshot`, `getContext`, `commit`, `setOwner`, `adoptRemote`, `subscribe`, `dispose` sont synchrones. Les budgets entrants/sortants et chaque notification sont copiés. Aucun callback de changement, adaptateur de persistance ou abonné ne reçoit la référence privée. L’écriture réussit avant publication ; un quota laisse l’état précédent intact. `getPublicationErrors()` expose les messages des abonnés défaillants de la dernière publication sans interrompre les autres abonnés. Les adaptateurs UI affichent alors l’avis de sauvegarde durable nécessitant un rechargement ; ils ne signalent pas un échec d’enregistrement. Le contrat de persistance est une fonction synchrone de stockage local, jamais une requête réseau.
- `clair/accounts/cloud.js` reste le seul synchroniseur : cache de transport, révision, dirty, operationId, CAS, retries, conflits, conversion et epoch Auth restent dans ce module. Son `record.payload` est la copie nécessaire au protocole de transport ; il ne constitue pas un second store UI. Les hooks `apply(payload,raw,{owner,epoch})` passent par l’adoption contrôlée de la session.
- `clair/accounts/account-ui.js` et le reste de `clair/app/index.template.html` adaptent les handlers et vues existants. L’alias `data` est une vue dérivée, en lecture seule par convention : seules l’initialisation depuis le store et sa subscription l’affectent. Les handlers modifient un brouillon `d` dans `commit`, jamais cet alias.

## Écriture et adoption

`commit` UI garde ses gardes Auth/conversion/conflit/récupération et son résultat booléen. Il compare le cache avec le snapshot brut attendu, puis délègue à la session et aux commandes. Le candidat est écrit avec l’enveloppe existante ; seulement ensuite il est publié. Les effets `afterLocalSave`, affichage, notification, push et son restent après l’écriture et ne peuvent convertir une réussite durable en échec. Une copie de récupération peut conserver le brouillon rejeté sans devenir l’état actif.

Chaque changement de propriétaire fournit explicitement l’owner et l’epoch de ClairCloud. Une adoption distante exige leur égalité exacte ; une génération ancienne ne peut devenir le nouveau contexte. La session refuse également un changement de contexte provoqué pendant la préparation avant d’appeler la persistance. Les gardes de formulaires/imports du lot2 restent nécessaires : elles vérifient aussi le budget et le snapshot capturés, pas uniquement le compte.

Chemins couverts : cache local initial/historique → `adoptRemote` ; entrée/sortie de compte → `setOwner` ; écriture manuelle/Express/épargne/setup/catégories/correction/suppression → `commit` ; import et reset confirmés → validation/persistance puis `adoptRemote` ; conversion/résolution/ACK/cloud → hook `apply` contrôlé ; événement storage ou cache concurrent détecté dans `commit` → `adoptCachedBudget`. Ce dernier utilise exclusivement `ClairCloud.decode` pour une copie de compte, vérifie propriétaire et metadata, adopte le budget et conserve la révision/dirty/operationId dans `Cloud.record`. Une copie d’un autre propriétaire est refusée sans adoption ni réécriture.

## ACK et cycle de vie des vues

La subscription du store publie un snapshot après chaque adoption ; elle ne fournit actuellement aucun indicateur `budgetChanged`. Le hook UI `apply` compare `JSON.stringify(E.normalize(next))` et `JSON.stringify(E.normalize(data))` **avant** l’adoption. Cette comparaison sémantique conserve les formulaires/wizard sur un ACK qui ajoute seulement des defaults ou des metadata Cloud ; une vraie modification garde la politique actuelle de fermeture des brouillons. Le raw et son `_cloud` servent au protocole/concurrence, pas à déterminer si une vue financière a changé. Le lot6 devra réutiliser cette comparaison normalisée ou ajouter un résultat sémantique au store ; comparer les JSON bruts distinguerait à tort une ligne Express peu remplie de sa normalisation.


`ui/page-host.js` possède uniquement la vue courante `{owner, page, view, inputs}`. `show(host, view, context)` monte, actualise seulement des dépendances différentes, ou dispose à la navigation ; `dispose()` est idempotent. Les vues fournissent `mount`, `update` et, si nécessaire, `dispose`. Aucun DOM de page inactive ni budget mutable supplémentaire n’est conservé. L’identité comprend owner/epoch, page, normalisation moteur, mois et jour civil Paris ; profil et réglages ajoutent leurs dépendances non financières (nom/email, push, installation, sons, conversion). Les branches Auth/récupération/erreur restent explicites, hors de cette optimisation. Le shell, rappels et compagnon sont actualisés même si le corps est inchangé.

`ui/navigation.js` partage la sélection primaire et conserve les boutons desktop. Le host mobile et toute la mécanique liquide de `accounts/glass-ui.js` restent inchangés. Le contrôleur journal reçoit un modèle nommé et ses dépendances de recherche, formatage et DOM ; il conserve les contrôles et réconcilie les lignes par ID, réutilisant les lignes identiques. Les états de recherche, détails, feedback/timer, trail et brouillon de charges sont purgés à chaque entrée/sortie de propriétaire, même si deux budgets sont identiques. Les ACK sémantiques conservent les dialogues ; une vraie modification distante garde la fermeture explicite historique.

`verify-render-lifecycle.cjs` vérifie le host et le DOM réel de l’HTML généré sur fixtures locales : clavier/focus, ACK, recherche/sélection/détails/scroll, édition et lignes réutilisées, mois/minuit Paris, statut réglages, nom/email profil, changement de propriétaire, récupération/logout, navigation rapide et listeners/observers bornés. Les anciens tests VM de handlers utilisent des adaptateurs de présentation uniquement après avoir vérifié la présence des modules canoniques ; ils ne prétendent pas vérifier le DOM navigateur.

## Assemblage et compatibilité

Le template contient des tokens pour moteur, commandes, session et modules historiques. Le générateur les insère dans les conteneurs existants : **cinq scripts, sept conteneurs**. L’index généré ne s’édite jamais à la main.

Le change reste lexicalement imbriqué dans `engine.js`. Les deux commentaires uniques `BEGIN/END GENERATED COMPATIBILITY exchange.js` délimitent l’unique source du fragment historique `accounts/exchange.js`. `mirrors.json` déclare `nestedIn` et `generatedFrom` : cette superposition est intentionnelle, le fragment imbriqué ne compte pas comme une deuxième position de script. `build.mjs --generate` régénère le fragment puis l’index ; `--check`, le checker des miroirs et la construction de paquet depuis Git rejettent un fragment périmé. `--generate --out` n’écrit pas dans le checkout et refuse une compatibilité périmée. La recette d’assemblage v2 rend ce changement explicite ; l’assemblage v1 des anciens commits reste supporté.

## Preuves et limites

Tests canoniques directs : domaine, dix ans de rattrapage, devises/change, métadonnées Express, commandes et session. Intégration : chargeur VM partagé `tools/clair/test-support/vm-loader.cjs`, handlers de l’HTML réellement généré, fixtures explicitement adoptées. Les suites compte/Express ne réinjectent plus les sources absentes. Le retrait des nouveaux modules fait échouer le démarrage testé. Le fixture Cloud utilise la vraie session et conserve les tests hors ligne/reconnexion, réponse perdue, conflits, conversions et changements rapides de comptes.

Les scripts CI Node/SQL/navigateur sont dans `clair-checks.yml`. Les SQL ne s’appliquent qu’en base locale jetable. Le navigateur teste HTTP, téléchargement et workers offline ; l’ouverture réelle `file://` reste NON EXÉCUTÉE dans l’environnement dont la politique Chromium la bloque. Les tests VM `location.protocol='file:'` constituent une preuve séparée, jamais un contournement ou une preuve navigateur. Aucun déploiement, base réelle, compte ou email réel n’est nécessaire à ces vérifications.
